# Indexing strategies across languages

> 当前已选 **方案 B（分阶段 IR 规范化）** 作为默认实现方向，下述其他方案保留作为对比参考。

下述方案围绕「不同语言语法各异，但索引结构相似」的原则，给出可选的索引流程设计，便于在 worker 启动后执行全量或增量索引。

## 方案 A：统一流水线 + 语言插件
- **统一步骤**：扫描 → 解析 → 抽取符号 → 写入 metadata / vector → 提交增量事件。
- **语言插件**：为每种语言提供 `Parser + SymbolExtractor`，输出统一的符号模型（文件/目录/类型/方法/文档注释）。
- **优势**：实现简单、共享监控与日志、易于首版落地。
- **适用场景**：项目语言较少、吞吐要求中等，希望快速上线。

## 方案 B：分阶段 IR 规范化
- **阶段化**：解析阶段按语言生成 AST → 中间表示（IR） → 符号模型。
- **IR 作用**：在 IR 中统一命名规则、修剪无关节点、补齐缺失信息（如推断方法可见性）。
- **优势**：跨语言一致性好，后续可复用 IR 做语义索引或调用链分析。
- **适用场景**：需要跨语言统一体验、未来扩展高级分析能力。
- **执行要点**：
  - worker 启动后优先准备 IR 标准库（命名规范、符号分类、位置字段），为后续语言插件复用。
  - 解析器输出语言特定 AST 后立即落盘/缓存 IR（便于断点续扫），再统一写入 metadata / vector。
  - IR 层记录 schema 版本，便于后续迁移或重新规范化。

## 方案 C：并行分片 + 资源隔离
- **并行策略**：按语言或目录分片，交由独立 worker 线程池并行解析，合并写入索引。
- **资源隔离**：为重量级语言（如 Java、C++）设定专属限流/内存阈值，避免拖慢轻量语言。
- **优势**：充分利用多核，提高大仓库的全量与增量吞吐。
- **适用场景**：大型单仓库、多语言共存、对索引速度敏感。

## 方案 D：按需懒加载 + 热路径优先
- **触发**：按 CLI/IDE 请求或文件热度，优先索引最常访问的模块，后台逐步补齐全量。
- **缓存**：对已加载模块缓存 AST/IR，结合 watcher 做局部刷新。
- **优势**：冷启动快，适合交互式“先可用后完善”。
- **适用场景**：开发机资源有限、对首次响应时间敏感。

## 共通配套（适用于各方案）
- **预检**：过滤二进制/生成物、尊重 `.gitignore`/自定义忽略列表。
- **幂等与断点续扫**：记录扫描游标与版本号，失败可重入；增量依赖 watcher + 变更队列。
- **日志与度量**：分阶段统计文件数、解析耗时、符号产出量；异常采样留档，便于回溯。
- **回写**：索引完成后更新 `.code-nav/metadata.db`、向量库与 worker 状态，供 `status/list` 查询。
- **可配置**：通过项目配置决定策略（如并行度、IR 级别、懒加载阈值）。
- **分支隔离**：推荐为长期存在的分支使用独立工作副本或 runtime 目录，每套 `.code-nav/` 独立维护 SQLite 与向量库，避免跨分支写锁竞争与数据污染；单副本切换分支时应在重大变更后触发一次增量/全量索引。
- **存储落地**：方案 B 对应的存储布局与 schema 详见 `index-storage-design.md`。
